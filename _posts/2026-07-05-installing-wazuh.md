## Installing and Integrating Wazuh with Suricata on pfSense

### Introduction

In my previous articles, I built a segmented cybersecurity homelab using Proxmox, pfSense, VLANs, and several intentionally vulnerable virtual machines for penetration testing. I also configured Suricata as a network intrusion detection system (NIDS) on pfSense to monitor traffic between the attack and server networks.

While Suricata is capable of detecting suspicious network activity, its alerts are stored locally on the firewall. As the number of monitored devices grows, manually reviewing logs becomes inefficient and makes incident investigation more difficult.

To solve this, Security Information and Event Management (SIEM) platforms such as Wazuh can be used to centralize security events from multiple systems, correlate alerts, and provide dashboards for monitoring and threat hunting.

In this article, I will install Wazuh on an Ubuntu Server virtual machine, deploy the Wazuh agent on pfSense, and integrate Suricata so that network intrusion alerts are automatically forwarded to the Wazuh platform. Finally, I will generate sample attacks from my Kali Linux machine to verify that the alerts are successfully collected and displayed in the Wazuh Threat Hunting dashboard.

At the end of this tutorial you will have:

- A dedicated Ubuntu 24.04 Wazuh server
- A pfSense firewall running the Wazuh agent
- Suricata forwarding IDS alerts
- A centralized SIEM dashboard
- Live Nmap detections visible in Threat Hunting

#### Prerequisites

This guide assumes you already have:

- Proxmox installed
- pfSense configured
- Suricata installed
- Kali Linux VM
- A vulnerable VM
- Basic VLAN routing working

## Detection Pipeline

The following diagram illustrates how a network attack is transformed into a security alert visible in the Wazuh dashboard.

![Suricata to Wazuh detection pipeline](/assets/img/blog16/image-2-detection-pipeline.webp)
*Figure 2: Detection pipeline showing how network traffic generated by an attack is inspected by Suricata, written to the eve.json log, collected by the Wazuh agent, processed by the Wazuh Manager, indexed, and finally visualized within the Wazuh dashboard.*

Instead of simply detecting malicious activity, this architecture provides an end-to-end monitoring pipeline that enables security analysts to investigate alerts from a centralized dashboard. When a scan or attack is launched from the Kali Linux attacker machine, Suricata inspects the network traffic and compares it against thousands of intrusion detection rules. Any matching events are written to the `eve.json` log file.

The Wazuh agent installed on pfSense continuously monitors this log file and securely forwards newly generated events to the Wazuh Manager. The manager then decodes the incoming events, applies detection rules, enriches the alerts with additional metadata, and stores them in the Wazuh Indexer. Finally, the processed alerts become searchable through the Wazuh Dashboard, where they can be investigated using the Threat Hunting interface.

## Part 1 - Deploying the Wazuh Server

### Download Ubuntu Server

The first step is to deploy a dedicated virtual machine that will host the Wazuh platform. Wazuh supports several Linux distributions, but Ubuntu Server 24.04 LTS is an excellent choice due to its long-term support, stability, and extensive documentation.

Download the latest Ubuntu Server 24.04 LTS ISO from the official Ubuntu release page: <https://releases.ubuntu.com/24.04/ubuntu-24.04.4-live-server-amd64.iso>

Alternatively, the ISO can be downloaded directly from the terminal using:

```bash
curl -L -o "ubuntu-24.04.4-live-server-amd64.iso" "https://releases.ubuntu.com/24.04/ubuntu-24.04.4-live-server-amd64.iso"
```

![Downloading Ubuntu Server 24.04 LTS ISO](/assets/img/blog16/1-download-ubuntu-24.04-live-server-ISO.webp)
*Figure 4: Downloading the Ubuntu Server 24.04.4 LTS installation image from the official Ubuntu release page.*

**Why Ubuntu Server?**

Wazuh is designed to run continuously as a server application. Ubuntu Server provides a lightweight operating system without a graphical desktop, reducing resource consumption while offering excellent package support and long-term security updates.

### Creating the Wazuh Virtual Machine

Once the ISO has been downloaded, create a new virtual machine within Proxmox VE.

For this deployment I allocated:

| Component | Allocation |
| :---: | :--- |
| **Memory** | 8 GB |
| **CPU** | 4 Cores |
| **Storage** | 100 GB |

![Proxmox virtual machine hardware summary](/assets/img/blog16/2-vm-hardware-summary.webp)
*Figure 5: Hardware configuration used for the Wazuh virtual machine.*

**Why 8 GB of RAM?**

Although Wazuh can run with fewer resources, the Wazuh Manager, Indexer, and Dashboard all execute on the same virtual machine in this lab. The Indexer is the most memory-intensive component because it stores and indexes security events for searching and visualization.
Allocating 8 GB of RAM ensures that all services can run simultaneously without excessive swapping while still leaving room for future log growth.

**Why 4 CPU Cores?**

The Wazuh Manager continuously receives events from agents, applies decoding rules, correlates alerts, and forwards data to the Indexer. At the same time, the Dashboard processes user queries and visualizations.
Using four CPU cores provides sufficient processing power for a homelab environment while maintaining responsive dashboard performance during scans and other security testing activities.

**Why a 100 GB Disk?**

Unlike traditional applications, SIEM platforms continuously collect and retain log data. As the number of monitored devices and security events increases, storage requirements also grow.
Allocating a 100 GB virtual disk provides enough capacity for the operating system, Wazuh components, package updates, and several weeks of retained security events generated during lab exercises.

### Installing the Wazuh Platform

With Ubuntu fully configured, the next step is to install the Wazuh platform.
Rather than manually installing each component individually, Wazuh provides an installation script that automatically installs and configures the Manager, Indexer, and Dashboard.

#### Download the installer

```bash
curl -sO https://packages.wazuh.com/4.14/wazuh-install.sh
```

The curl utility downloads the installation script directly from the official Wazuh package repository. The -s option suppresses unnecessary output, while -O saves the file using its original filename.

#### Make the script executable

```bash
chmod +x wazuh-install.sh
```

Linux treats downloaded files as ordinary files until execute permissions are granted. The chmod +x command adds executable permissions, allowing the script to be run like a normal program.

#### Begin the installation

```bash
sudo bash ./wazuh-install.sh -a
```

The -a option performs an all-in-one installation, automatically deploying:

- Wazuh Manager
- Wazuh Indexer
- Wazuh Dashboard

on the same server.

![Downloading and installing Wazuh](/assets/img/blog16/3-download-and-install-wazuh.webp)
*Figure 8: Downloading the Wazuh installation script and performing an all-in-one installation.*

Depending on your internet connection and system resources, the installation typically takes between **15 and 30 minutes.**
During this process, the installer downloads packages, generates certificates, configures internal communication between Wazuh components, installs required dependencies, and starts the necessary services automatically.

## Part 2 – Integrating pfSense with Wazuh

At this point, the Wazuh server is fully operational. However, it is not yet monitoring any devices. To collect security events from pfSense, we first need to install the Wazuh agent on the firewall and configure it to communicate with the Wazuh Manager.

Once the agent has been deployed, we will configure it to monitor Suricata's JSON log file (eve.json). Every time Suricata detects suspicious network activity, the generated alerts will be collected by the agent and securely forwarded to the Wazuh Manager for processing and visualization.

**Understanding eve.json**

Suricata supports multiple output formats. The eve.json file is its primary structured logging format and contains detailed information about every inspected network event, including alerts, flows, DNS queries, HTTP requests, TLS handshakes, and protocol metadata. Wazuh parses this JSON format directly, making it ideal for SIEM integration.

### Installing the Wazuh Agent on pfSense

Unlike a standard FreeBSD installation, pfSense intentionally disables access to the official FreeBSD package repositories.

This is because pfSense is distributed as a security appliance with a carefully tested package ecosystem. Allowing unrestricted installation of packages from the FreeBSD repositories could introduce dependency conflicts or incompatible software versions, potentially affecting firewall stability.

Since the Wazuh agent is not included in the default pfSense package repository, we must **temporarily** enable access to the official FreeBSD packages.

#### Enabling the FreeBSD Repository

From the pfSense shell, open the repository configuration file located at:

```bash
/usr/local/etc/pkg/repos/pfSense.conf
```

Locate the following section:

```text
FreeBSD: {
    enabled: no
}
```

![pfSense repository configuration before modification](/assets/img/blog16/10-pfsense-conf-freeBSD-no.webp)
*Figure 15: The FreeBSD package repository is disabled by default in pfSense.*

Change it to:

```text
FreeBSD: {
    enabled: yes
}
```

![Enabling the FreeBSD repository](/assets/img/blog16/11-pfsense-conf-freeBSD-yes.webp)
*Figure 16: Enabling the official FreeBSD package repository.*

This change allows the package manager to retrieve packages that are not available through the pfSense repositories, including the Wazuh agent.

**🛑 Note**:
Enabling the FreeBSD repository should only be done when required. Installing arbitrary FreeBSD packages on a production firewall is generally discouraged because they are not tested by the pfSense developers.

#### Configuring the FreeBSD Repository

Next, edit the following file:

```bash
/usr/local/etc/pkg/repos/FreeBSD.conf
```

Replace its contents with:

```bash
FreeBSD: {
   url: "pkg+http://pkg.FreeBSD.org/${ABI}/quarterly",
   mirror_type: "srv",
   signature_type: "fingerprints",
   fingerprints: "/usr/share/keys/pkg",
   enabled: yes
}
```

![FreeBSD repository configuration](/assets/img/blog16/12-FreeBSD-conf.webp)
*Figure 17: Configuring the official FreeBSD Quarterly package repository.*

Let's briefly look at what each option does.

| Setting | Purpose |
| :---: | :--- |
| url | Specifies the official FreeBSD package repository. |
| mirror_type | Automatically selects a nearby package mirror. |
| signature_type | Verifies downloaded packages using digital signatures. |
| fingerprints | Specifies the trusted public keys used for package verification. |
| enabled | Enables this repository for package downloads. |

Using the **Quarterly** repository provides a more stable package set compared to the **Latest** branch, making it a better choice for security appliances.

### Refreshing the Package Database

Now that the FreeBSD repository has been enabled, refresh the package manager.

First remove any cached package metadata.

```bash
pkg clean -a
```

This command deletes locally cached package files that may reference outdated repositories.

Next, force the package manager to download the latest repository metadata.

```bash
pkg update -f
```

The -f flag forces a complete refresh, even if the repository appears to be up to date.

![Updating FreeBSD package repositories](/assets/img/blog16/13-FreeBSD-package-update.webp)
*Figure 18: Refreshing the FreeBSD package repository metadata.*

This step ensures that the package manager is aware of the newly enabled repository before attempting to install the Wazuh agent.

#### What is the Wazuh Agent?

The Wazuh agent is a lightweight application installed on monitored systems. Think of it as the **sensor** that collects security information from an endpoint.

Depending on the operating system, an agent can monitor:

- System logs
- Authentication events
- File integrity changes
- Running processes
- Installed software
- Security configurations
- IDS logs such as Suricata

Rather than continuously polling the Wazuh server, The Wazuh agent continuously monitors local log sources and securely forwards collected events to the Wazuh Manager in near real time.

In our environment, the pfSense firewall is running both Suricata and the Wazuh agent.

This means the workflow is:

```mermaid
Suricata
      │
      ▼
eve.json
      │
      ▼
Wazuh Agent
      │
      ▼
Wazuh Manager
```

Instead of the Wazuh Manager reading log files directly from pfSense, the agent performs that task locally and forwards the events over an encrypted connection.

### Configuring the Wazuh Agent

After installation, the agent still doesn't know where the Wazuh Manager is located.

That information is stored in:

```bash
/var/ossec/etc/ossec.conf
```

Open the configuration file and locate the **client** section.

Initially, it looks similar to:

```bash
<address>IP</address>
```

![Default Wazuh Manager address](/assets/img/blog16/16-ossec-conf-client-IP.webp)
*Figure 21: Default manager address before configuration.*

Replace the placeholder with the IP address of your Wazuh server.

For example:

```bash
<address>10.10.99.50</address>
```

![Updated Wazuh Manager IP address](/assets/img/blog16/17-ossec-conf-client-IP-to-wazuh-ip.webp)
*Figure 22: Configuring the Wazuh agent to communicate with the Wazuh Manager.*

This tells the agent exactly where to send all collected security events. Without configuring this address, the agent has no destination and cannot register with the manager.

### Starting the Agent

Once the configuration has been updated, enable and restart the service.

```bash
service wazuh-agent enable
service wazuh-agent restart
```

The first command enables the service so it starts automatically whenever pfSense boots. The second command starts the agent immediately using the updated configuration.

### Integrating Suricata with Wazuh

Although the Wazuh agent is now connected, it is not yet collecting Suricata alerts. Suricata stores all network events inside the **eve.json** log file. Wazuh needs to know where this file is located before it can begin processing IDS alerts.

Edit:

```bash
/var/ossec/etc/ossec.conf
```

Inside the **ossec_config** section, add:

```bash
<localfile>
    <log_format>json</log_format>
    <location>/var/log/suricata/*/eve.json</location>
</localfile>
```

![Configuring Wazuh to monitor Suricata eve.json](/assets/img/blog16/19-setup-suricata-eve-json-location.webp)
*Figure 24: Configuring the Wazuh agent to monitor the Suricata `eve.json` log file.*

The eve.json file is generated automatically by Suricata and contains structured JSON records describing every detected event.

The wildcard (*) is important because pfSense creates a separate log directory for each monitored Suricata interface. Rather than specifying a single directory, the wildcard allows Wazuh to monitor the eve.json file regardless of which interface generated it.

This makes the configuration more flexible and ensures alerts from all monitored interfaces are collected.

### Verifying Log Collection

Restart the Wazuh agent (or reboot the VM) so the new configuration is loaded.

On the Wazuh server, monitor the alert log:

```bash
sudo tail -f /var/ossec/logs/alerts/alerts.json
```

- eve.json = generated by Suricata
- alerts.json = generated by Wazuh

![Viewing alerts.json](/assets/img/blog16/20-wazuh-alerts-json-file.webp)
*Figure 25: Confirming that Suricata alerts are being received and written to the Wazuh `alerts.json` file.*

If the integration is working correctly, new Suricata alerts will begin appearing in real time.
This is an important milestone because it confirms that the entire collection pipeline—from Suricata, through the Wazuh agent, to the Wazuh Manager—is functioning correctly.

### Generating Test Traffic

At this point, the installation is complete. The remaining sections focus on validating that the entire detection pipeline functions correctly by generating real network traffic. Before launching the scan, verify that the Kali Linux virtual machine can communicate with the vulnerable target located in the Server VLAN.

In my lab, the vulnerable machine is located at: 10.10.20.x

To generate reconnaissance traffic, execute the following command from the Kali terminal:

```bash

```

![Running an Nmap service version scan from Kali Linux](/assets/img/blog16/22-kali-nmap-sample-attack.webp)
*Figure 28: Performing an Nmap service version scan against a vulnerable virtual machine from the attacker network.*

The -sV option instructs Nmap to perform service version detection. Instead of simply identifying open ports, Nmap sends a series of application-layer probes to determine which services are running and, where possible, their version numbers.

Because these probes intentionally interact with multiple network services, they generate traffic that closely resembles reconnaissance activity performed during the early stages of a penetration test. This makes them ideal for validating intrusion detection systems such as Suricata.

#### Why use Nmap?

Nmap is one of the most widely used reconnaissance tools in both penetration testing and defensive security. Since many attackers begin by identifying open ports and services, detecting Nmap scans is a common and useful capability for an IDS.

During the Nmap scan, several different Suricata signatures were triggered. Two of the most interesting are discussed below.

#### ET SCAN Possible Nmap User-Agent Observed

One of the alerts generated during testing is:

**ET SCAN Possible Nmap User-Agent Observed**

This rule originates from the **Emerging Threats (ET Open)** rule set.

When Nmap performs version detection (-sV), it may send HTTP requests containing a User-Agent string that identifies itself as Nmap Scripting Engine or another Nmap-related identifier.
The Emerging Threats rule detects this distinctive User-Agent and generates an alert indicating that Nmap reconnaissance has likely been observed.
Although this activity is not necessarily malicious, it is often associated with the reconnaissance phase of an attack and therefore provides valuable context for security analysts.

#### SURICATA AppLayer Detect Protocol Only One Direction

Another alert generated during testing is:

**SURICATA Applayer Detect protocol only one direction**

At first glance, this alert appears unusual, but it is generally considered an informational protocol parsing event rather than evidence of an attack.

Suricata attempts to identify application-layer protocols by observing traffic flowing in both directions of a connection.

During service detection, Nmap frequently sends probes that do not establish a complete application-layer conversation.

As a result, Suricata may only observe one side of the protocol exchange and generate this alert.

In most homelab environments, this alert is expected during aggressive scanning and does not necessarily indicate malicious behaviour beyond the reconnaissance activity already taking place.

| :---: | :--- |
| **Timestamp** | Time the event occurred |
| **Agent** | Device that forwarded the alert (pfSense) |
| **Rule ID** | Wazuh rule responsible for processing the event |
| **Rule Description** | Human-readable explanation of the detection |
| **Severity Level** | Wazuh alert level assigned to the event |
| **Source IP** | Originating system (Kali Linux) |
| **Destination IP** | Target system (vulnerable VM) |
| **Source Port** | Source network port |
| **Destination Port** | Target network port |
| **Protocol** | TCP, UDP, ICMP, etc. |
| **Signature ID** | Original Suricata rule identifier |
| **Flow ID** | Unique identifier for the network session |
| **Interface** | Network interface that observed the traffic |
| **Payload** | Captured packet data (when available) |

Having access to this level of detail enables analysts to reconstruct network activity, determine which hosts were involved, identify the triggering detection rule, and correlate related events during an investigation.
